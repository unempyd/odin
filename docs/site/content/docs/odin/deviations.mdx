Stated plainly, because independent reviews returned NOT FINISHED twice and
FINISHED WITH MATERIAL DEVIATIONS after that against `odin/DIRECTION.md`'s
definition of done. These are the items that remain open by decision, not by
oversight — each with the reason.

## 1. Status is not yet single-writer end to end

The main-process store is single-writer. The renderer is still a second writer
for remote-runtime panes whose bytes never transit the host, and it still merges
client identity fields into host rows.

<Callout title="What closed, and what is left">
  `odin/OPEN.md` classifies every `setAgentStatus(` call site. The structured
  chat bridge closed outright (status-A: main now forwards structured rows over
  `agentStatus:set` like any hook row). The background-status consumer, the
  automation-session observer and the direct-SSH retry writer closed for local
  and SSH panes and are gated for remote-runtime panes on the
  `agent-status.host-osc-ingest.v1` capability (status-C, status-D-fix) — a
  capable host's row makes the client write a no-op; an old host's pane keeps
  exactly today's write, and the cold-cache first write defaults to the client
  writing until a probe resolves.
</Callout>

The renderer is also still the only writer of a pane's very first `working`
row, seeded from its own launch config before any host observation exists
(`title-spawn-bell.ts`'s `applyInitialAgentStatus`,
`command-code-prompt-status-seed.ts`, `launch-agent-background-session.ts`) — a
launch-time seed for local panes exactly as much as remote ones, and not one of
the call sites the closing plan covers. Odin removed the cross-machine
wall-clock adjudication (contract **S**) and the writers named above, and
nothing more.

## 2. Settlement keeps two positive-evidence exceptions

An explicit idle marker or ready prompt the agent itself paints counts as
observation (a fresh first-party working status now vetoes it), and agents whose
only rest signal is their name (grok, copilot, aider, mimo, agy, opencode)
settle after the quiescence window. Removing the second would make `tui-idle`
unusable for those agents
([#6011](https://github.com/stablyai/orca/issues/6011)) — it is a named
trade-off, not the pure "silence is unverifiable" rule.

## 3. The wait result shape is Orca's, not the literal three-valued type

The wait result is `satisfied` plus `evidence`, not the literal
`accepted | refused | unverifiable` type. The three outcomes are representable
and every silence path maps to not-satisfied, but the wire shape is kept for
compatibility.

## 4. Worker observation keeps legacy wire values

`unattached`, `missing` and `identity_changed` stay beside
`live / unverifiable / exited` because clients depend on them as distinct
states.

## 5. The launch receipt verifies advertised support, not applied options

`source: 'probe'` means the installed CLI listed the model — and, for Claude,
the effort too — *and* the discovery answer's own `catalogOrigin` says the
listing came from that live probe rather than a static-catalog fallback (I4).
For Codex and Cursor, effort is validated against the static catalog
(`effortSource: 'catalog'`): Codex's `debug models` never lists `minimal`,
which the catalog treats as universal, and Cursor's probe derives
`thinkingLevels` from an id-pattern heuristic that doesn't cover every model the
catalog gives a real `effort` option (I3) — trusting the probe in either case
would reject a valid selection. Grok has no live probe at this receipt at all;
its catalog does not opt into worker launch preferences, so a grok
`--model`/`--effort` worker-start is rejected before any receipt exists.
Nothing reads back what the launched session actually applied, for any agent.

## 6. Sub-agent rows are still renderer-derived

They carry their own identity now (contract **K**), but their synthesized entry
state falls back to `done` where the status type has no `unverifiable` member.

## 7. Proof coverage is macOS plus a Linux container

Windows process ownership, mixed-version clients, mobile pairing against an Odin
host, and a third agent settling (this operator's Grok quota) are not
established by the recorded runs. SSH-hosted worktrees *are* covered end to end:
`odin/proof/ssh-boundary.mjs` runs a real desktop-mode host against a real VPS
and proves target/repo registration, a real `ssh.connect` relay deploy reaching
`connected`, worktree and terminal creation on the SSH host, and the
loss-of-contact matrix (transport drop, relay `SIGKILL`, reconnect,
owner-proven exit). Three real bugs were found and fixed along the way: a
dev-mode relay-path resolution gap, a symlinked-worktree upload-root false
rejection, and a headless/background launch hanging forever inside a synchronous
macOS Keychain call. Still open: `terminal wait --for exit`'s immediate-silence
verdict on real transport loss is proven only by unit tests, not by that run.

## 8. Retained telemetry opt-ins are preserved for existing profiles

Only fresh installs are opted out (contract **F**); a pre-existing profile that
was auto-enrolled by Orca's former migration keeps that choice until the
operator changes it in Settings.

## 9. Cost accounting does not exist

`DIRECTION.md`'s build-order item 5, "cost/resource accounting on the graph", is
half delivered. Resource accounting is real — contract **N**'s `dispatched_at`,
`exit_code` and `wallclockMs` on `worker-show --json`. Cost/token accounting
does not exist anywhere in the orchestration tree: no wired path records what a
dispatch spent. Nothing in the repository claims otherwise, but the build-order
item itself is not fully met.

## 10. Two adjacent process-liveness vocabularies exist

Beside the fixed `live` / `unverifiable` / `exited` vocabulary, two local-only
questions the SSH boundary contract does not cover keep their own words:
`daemon-audit-classifier.ts`'s `present` / `gone` / `unknown` (is the local
terminal daemon process running) and `orca-runtime-get-worktree-ps.ts`'s
`live` / `dead` / `unknown` (recovering a structured session's local PID after a
restart). Neither ever observes a worker's PTY across the relay/SSH boundary, so
neither is a synonym in the sense `DIRECTION.md` item 4 forbids — but a reader
tracing "what counts as liveness here" needs both named.
`docs/reference/ssh-execution-boundary.md` states the scope, and names the
related hazard that `terminal_gone` used to be thrown with two different
evidentiary strengths (now separated — residual **O3b**).

## 11. The `safeStorage` windowless guard is reached only by flagged launches

Only launches that set `ORCA_BACKGROUND_LAUNCH` or run E2E-headless — proof
drivers, tests, benchmarks — reach the guard; no production or user-facing
launch path sets either. Under that flag, and scoped to macOS (the only platform
with a Keychain prompt that can hang with no window to answer it),
`ElectronSecretStore` reports encryption unavailable instead of touching
`safeStorage`. That degrades four callers differently: protected settings and
the SSH PTY owner lease are not persisted; the MiniMax API key/cookie are
written in plaintext with a console warning; plugin secrets refuse to read or
write; a saved cloud session reads back as `decrypt-failed`. The real-world
hidden-launch variant of the same hang — Orca started by a login item with a
window created but never shown, and no env flag set — is not proven fixed.

## 12. A reader-side precedence rule exists for command-code status

`dropsCommandCodeAgentStatus` drops a host-published command-code row when
renderer-local state (foreground process, retained agent, launch config)
disagrees about which agent currently owns the pane. Main cannot decide this
itself — foreground and retained-agent ownership is renderer-only state it never
sees — so the filter stays client-side. `DIRECTION.md` item 2's "no reader-side
precedence" is not met here; removing it needs main to track pane-level agent
ownership itself, which is out of scope for this increment.

---

Everything above is either tracked with a plan in
[`odin/OPEN.md`](https://github.com/unempyd/odin/blob/main/odin/OPEN.md), or
accepted for v1.0.0 as Orca's existing behaviour.
